# The KV Cache: From First Principles to Exact Memory Arithmetic

The KV cache is one of the most important ideas in LLM inference because it explains a surprisingly large part of why generating text becomes expensive as the conversation gets longer. If you understand the KV cache properly, you can derive how much GPU memory a model needs for inference, understand why long-context inference consumes enormous amounts of VRAM, understand the difference between MHA, MQA, and GQA, and understand optimizations such as paged attention, KV-cache quantization, prefix caching, and cross-model KV transfer.

I will build the concept from the beginning, without assuming that you already know attention internals, and I will do the actual arithmetic using a real model configuration: **Llama 3 / Llama 3.1 8B-style architecture with 32 layers, 32 query heads, 8 KV heads, and head dimension 128**.

---

# 1. First, what happens when an LLM generates text?

Suppose you ask:

> "Explain quantum computing in simple words."

The model does not process this as one giant English sentence internally. The text is first converted into tokens.

For example, conceptually:

```text
"Explain quantum computing in simple words."
        ↓
["Explain", " quantum", " computing", " in", " simple", " words", "."]
```

The exact tokens depend on the tokenizer.

These tokens are converted into vectors called embeddings, and those vectors pass through the transformer layers.

A simplified transformer looks like this:

```text
Text
  ↓
Tokenizer
  ↓
Token IDs
  ↓
Embeddings
  ↓
Transformer Layer 1
  ↓
Transformer Layer 2
  ↓
Transformer Layer 3
  ↓
...
  ↓
Transformer Layer N
  ↓
Logits
  ↓
Next-token prediction
```

Suppose the model predicts:

```text
"Quantum"
```

Then the generated token is appended to the existing sequence:

```text
Explain quantum computing in simple words. Quantum
```

The model then predicts the next token.

Perhaps:

```text
"computing"
```

Now the sequence becomes:

```text
Explain quantum computing in simple words. Quantum computing
```

And this continues token by token.

This is where an important problem appears.

---

# 2. The naive approach would be extremely wasteful

Imagine that the prompt contains 10,000 tokens.

The model needs to generate one additional token.

A naive implementation could process all 10,001 tokens again.

Then it generates another token.

Now it processes all 10,002 tokens again.

Then:

```text
10,003
10,004
10,005
...
```

This would repeatedly perform work for tokens whose representations have not changed.

The earlier tokens are not changing.

If the model has already processed:

```text
The capital of France is
```

and is now generating:

```text
Paris
```

the representation of:

```text
The
capital
of
France
is
```

doesn't suddenly change merely because we're generating the next token.

So why calculate the same information repeatedly?

This is the fundamental motivation behind the **KV cache**.

---

# 3. Before understanding the cache, understand Q, K and V

Transformer attention uses three important objects:

```text
Q = Query
K = Key
V = Value
```

You can think about them in simple terms.

The **Query** represents:

> "What information am I looking for?"

The **Key** represents:

> "What information do I contain, and when should I be considered relevant?"

The **Value** represents:

> "What information should actually be retrieved if I'm relevant?"

For every token, the transformer generates these representations.

For example, imagine:

```text
The cat sat on the mat
```

When processing the token:

```text
mat
```

the model might effectively ask:

> "Which previous tokens are relevant to understanding what comes next?"

The query for the current token interacts with the keys of previous tokens.

The resulting attention scores determine how much information should be retrieved from the corresponding values.

Conceptually:

```text
Current token
     |
     | creates Query
     ↓
   Query
     |
     | compares against
     ↓
Previous Keys
     |
     | produces attention scores
     ↓
Attention weights
     |
     | retrieves information from
     ↓
Previous Values
```

That is the core mechanism.

---

# 4. The important observation

Suppose we have already processed these tokens:

```text
A B C D E
```

When we are generating the next token, the model needs the keys and values associated with:

```text
A B C D E
```

Those keys and values do not need to be calculated again.

They can simply be stored.

That stored information is the:

# KV Cache

The name literally means:

```text
K = Key
V = Value

KV Cache = cached Keys + cached Values
```

The cache stores the K and V tensors generated by previous tokens.

---

# 5. Why don't we cache Q?

This is a very important question.

Why is it called:

```text
KV cache
```

instead of:

```text
QKV cache
```

The reason is that during autoregressive generation, the query for the newly generated token is needed only once for that generation step.

Suppose we have:

```text
Token 1
Token 2
Token 3
Token 4
Token 5
```

We already have cached K and V for tokens 1 through 5.

Now we generate token 6.

We calculate:

```text
Q6
K6
V6
```

We append:

```text
K6
V6
```

to the cache.

Then we use:

```text
Q6
```

to attend over:

```text
K1 K2 K3 K4 K5 K6
```

and:

```text
V1 V2 V3 V4 V5 V6
```

After the next token arrives, Q6 isn't needed anymore.

We need:

```text
Q7
```

instead.

So there is little benefit to keeping the previous queries around.

The cache therefore stores:

```text
K1 K2 K3 K4 K5 K6
V1 V2 V3 V4 V5 V6
```

but not:

```text
Q1 Q2 Q3 Q4 Q5 Q6
```

---

# 6. What exactly is stored?

Let's go one level deeper.

A transformer has multiple layers.

Suppose the model has:

```text
32 transformer layers
```

Every layer performs its own attention operation.

Therefore, each layer has its own K and V tensors.

The cache isn't simply:

```text
K
V
```

Instead, it is approximately:

```text
Layer 1
    K cache
    V cache

Layer 2
    K cache
    V cache

Layer 3
    K cache
    V cache

...

Layer 32
    K cache
    V cache
```

And every generated token adds another K/V entry to every layer.

This is why the KV cache grows with:

```text
number of layers
×
number of tokens
×
number of KV heads
×
head dimension
×
2
×
bytes per element
```

That equation is the heart of KV-cache memory calculation.

---

# 7. Deriving the exact per-token formula

Let's derive it instead of memorizing it.

For one token, one layer, one KV head, the key vector contains:

```text
head_dim
```

numbers.

The value vector also contains:

```text
head_dim
```

numbers.

So one token requires:

```text
head_dim
+
head_dim
```

elements.

That is:

```text
2 × head_dim
```

elements.

Now suppose the model has:

```text
num_kv_heads
```

KV heads.

Then:

```text
2 × num_kv_heads × head_dim
```

elements are required per token per layer.

Now suppose there are:

```text
num_layers
```

layers.

Therefore:

```text
2 × num_layers × num_kv_heads × head_dim
```

elements are required per token.

Finally, each element consumes some number of bytes.

For BF16:

```text
2 bytes
```

For FP16:

```text
2 bytes
```

For FP32:

```text
4 bytes
```

For FP8:

```text
1 byte
```

So the general formula is:

```text
KV-cache bytes per token

=
2
×
number of layers
×
number of KV heads
×
head dimension
×
bytes per element
```

That is the exact basic formula.

---

# 8. The most important distinction: KV heads are NOT necessarily attention heads

This is where many KV-cache calculations go wrong.

Older transformer architectures commonly used **Multi-Head Attention**, or MHA.

If a model had:

```text
32 attention heads
```

it might also have:

```text
32 KV heads
```

But modern LLMs frequently use:

```text
GQA
```

which means:

> Grouped Query Attention.

In GQA, there are more query heads than KV heads.

For example:

```text
Query heads = 32
KV heads    = 8
```

The 32 query heads are grouped around only 8 KV heads.

Conceptually:

```text
Q1  Q2  Q3  Q4  → KV1
Q5  Q6  Q7  Q8  → KV2
Q9  Q10 Q11 Q12 → KV3
...
```

The exact grouping depends on the architecture, but the important point is:

```text
KV heads < Query heads
```

This dramatically reduces KV-cache memory.

# 9. Real example: Llama 3 8B-style architecture

Let's calculate an actual model.

Consider the 8B Llama architecture with these relevant attention parameters:

```text
Number of transformer layers = 32

Query attention heads = 32

KV heads = 8

Head dimension = 128

KV data type = BF16

BF16 = 2 bytes
```

Notice something important.

We do NOT use:

```text
32 query heads
```

in the KV-cache formula.

We use:

```text
8 KV heads
```

because only the KV heads are cached.

Now let's calculate it.

---

# 10. Step 1: Calculate one Key vector

One KV head has:

```text
128 values
```

So one Key vector contains:

```text
128 elements
```

Because we are using BF16:

```text
128 × 2 bytes
```

which gives:

```text
256 bytes
```

So one Key for one KV head requires:

```text
256 bytes
```

---

# 11. Step 2: Calculate one Value vector

The Value vector has the same shape.

Therefore:

```text
128 × 2
```

equals:

```text
256 bytes
```

So:

```text
Key   = 256 bytes
Value = 256 bytes
```

Together:

```text
256 + 256 = 512 bytes
```

for one KV head for one token in one layer.

---

# 12. Step 3: There are 8 KV heads

We have:

```text
8 KV heads
```

Therefore:

```text
512 × 8
```

equals:

```text
4,096 bytes
```

So one token requires:

```text
4,096 bytes
```

of KV-cache memory per layer.

That's:

```text
4 KB
```

approximately.

---

# 13. Step 4: There are 32 layers

Now multiply by:

```text
32 layers
```

Therefore:

```text
4,096 × 32
```

equals:

```text
131,072 bytes
```

So:

# One token requires 131,072 bytes of KV cache.

Convert that.

```text
131,072 bytes
÷ 1024
=
128 KiB
```

Therefore:

# One token = 128 KiB of KV cache.

This is an extremely useful number.

For this architecture, under BF16:

```text
1 generated token
≈ 128 KiB KV cache
```

---

If one token requires:

```text
131,072 bytes
```

then:

```text
131,072 × 1,000
```

equals:

```text
131,072,000 bytes
```

Approximately:

```text
125 MiB
```

So:

```text
1,000 tokens
≈ 125 MiB
```

of KV cache.

# 15. What about 4,000 tokens?

Now:

```text
131,072 × 4,000
```

equals:

```text
524,288,000 bytes
```

That's approximately:

```text
500 MiB
```

So:

```text
4K tokens
≈ 500 MiB
```

of KV cache.

# 16. What about 8K context?

Now we calculate:

```text
131,072 × 8,192
```

The result is:

```text
1,073,741,824 bytes
```

```text
1 GiB
```

# 8K tokens require approximately 1 GiB of KV cache.

This is the reason context length matters so much.

A model may have billions of parameters, but the model weights themselves are relatively fixed during inference.

The KV cache is different.

It grows continuously with sequence length.

# 21. Notice something surprising

The model is called:

```text
8B
```

because it has roughly eight billion parameters.

But the KV cache does not care directly that the model has eight billion parameters.

The KV cache depends primarily on:

```text
number of layers
number of KV heads
head dimension
context length
KV precision
```

This is a very important distinction.

The memory for model weights is approximately:

```text
number of parameters × bytes per parameter
```

while KV-cache memory is approximately:

```text
tokens × layers × KV heads × head dimension × 2 × bytes
```

These are two completely different memory consumers.

# 22. Model weights versus KV cache

Suppose our 8B model is stored in BF16.

Each parameter requires approximately:

```text
2 bytes
```

So the raw weight memory is approximately:

```text
8 billion × 2 bytes
```

which is around:

```text
16 GB
```

before accounting for other runtime memory and implementation details.

Now consider a 128K context.

The KV cache alone can require:

```text
16 GiB
```

for the architecture we calculated.

So you can conceptually have:

```text
Model weights
≈ 16 GB

KV cache
≈ 16 GiB

Other memory
≈ additional VRAM
```

This explains why a model that fits comfortably at short context can become difficult to serve at very long context.

---

# 23. Why does the KV cache grow linearly?

This is another fundamental concept.

Suppose you have:

```text
1 token
```

You store:

```text
K1
V1
```

For:

```text
2 tokens
```

you store:

```text
K1 V1
K2 V2
```

For:

```text
3 tokens
```

you store:

```text
K1 V1
K2 V2
K3 V3
```

Therefore:

```text
tokens ↑
    ↓
KV cache ↑
```

The relationship is approximately linear.

If:

```text
1 token = 128 KiB
```

then:

```text
10 tokens = 1,280 KiB
100 tokens = 12,800 KiB
1,000 tokens = 128,000 KiB
10,000 tokens = 1,280,000 KiB
```

So doubling context approximately doubles KV-cache memory.

---

# 24. Why doesn't compute grow in exactly the same way?

There is an interesting distinction between memory and computation.

During generation, we only generate one new token at a time.

For the new token, its Query needs to interact with all previous Keys.

Suppose the sequence contains:

```text
10,000 tokens
```

The new Query has to attend across approximately:

```text
10,000 Keys
```

So attention computation grows with sequence length.

Meanwhile, the KV cache also grows with sequence length.

This produces the familiar behavior of long-context inference:

```text
Longer context
     ↓
More KV memory
     ↓
More attention work per generated token
     ↓
Higher latency / memory pressure
```

This is why serving long-context models efficiently is difficult.

---

# 25. What happens during the first prompt?

There are actually two important phases in LLM inference.

The first is usually called:

```text
Prefill
```

The second is:

```text
Decode
```

Suppose your prompt is:

```text
Explain transformer architecture in detail.
```

containing 1,000 tokens.

During prefill, the model processes the prompt and creates the K and V tensors for those tokens.

Conceptually:

```text
1,000 prompt tokens
        ↓
Transformer
        ↓
K/V generated for every layer
        ↓
KV cache populated
```

After that, the model generates a new token.

---

# 26. Decode phase

Suppose the model generates:

```text
"The"
```

Now the cache contains the original prompt plus the generated token.

Then it generates:

```text
transformer
```

Then:

```text
architecture
```

and so on.

The cache keeps growing:

```text
Prompt
  ↓
K/V cache

Prompt + token 1
  ↓
larger K/V cache

Prompt + token 1 + token 2
  ↓
larger K/V cache

Prompt + token 1 + token 2 + token 3
  ↓
larger K/V cache
```

This is why decoding is sometimes described as:

> Read from the existing KV cache, compute the new token's Q/K/V, append K/V, and generate the next token.

---

# 27. The actual attention process during decoding

Suppose we have already processed:

```text
Token 1
Token 2
Token 3
Token 4
Token 5
```

The cache contains:

```text
K1 K2 K3 K4 K5
V1 V2 V3 V4 V5
```

Now token 6 arrives.

The model computes:

```text
Q6
K6
V6
```

Then:

```text
Q6
```

is compared with:

```text
K1 K2 K3 K4 K5 K6
```

The resulting attention weights are used to combine:

```text
V1 V2 V3 V4 V5 V6
```

The resulting representation is passed through the rest of the transformer computation.

Then the model predicts token 7.

The important optimization is that the model does NOT need to recompute:

```text
K1
V1
K2
V2
...
K5
V5
```

They already exist in memory.

That's the entire reason the KV cache exists.

---

# 28. What would happen without the KV cache?

Without caching, every new token would force the model to regenerate K and V for every previous token.

For example:

```text
Step 1:
calculate K1 V1

Step 2:
calculate K1 V1
calculate K2 V2

Step 3:
calculate K1 V1
calculate K2 V2
calculate K3 V3

Step 4:
calculate K1 V1
calculate K2 V2
calculate K3 V3
calculate K4 V4
```

The same computation is repeated again and again.

With caching:

```text
Step 1:
calculate K1 V1
store them

Step 2:
reuse K1 V1
calculate K2 V2
store them

Step 3:
reuse K1 V1 K2 V2
calculate K3 V3
store them
```

This is much more efficient.

---

# 29. The cache is basically a memory-speed tradeoff

The KV cache doesn't make computation disappear magically.

Instead, we exchange:

```text
repeated computation
```

for:

```text
memory consumption
```

We calculate K/V once and store them.

Then we reuse them.

So the fundamental trade-off is:

```text
More VRAM
    ↓
Larger KV cache
    ↓
Less redundant computation
    ↓
Faster generation
```

This is one of the classic ideas in computer architecture:

> Spend memory to save computation.

---

# 30. Why GQA is such a big deal

Now we can understand why GQA is so useful.

Suppose the model had:

```text
32 query heads
32 KV heads
```

instead of:

```text
32 query heads
8 KV heads
```

The KV-cache memory would become four times larger.

Why?

Because:

```text
32 / 8 = 4
```

So with full multi-head attention:

```text
1 token ≈ 512 KiB
```

instead of:

```text
1 token ≈ 128 KiB
```

for our example architecture.

At 128K context:

```text
512 KiB × 131,072
```

would produce approximately:

```text
64 GiB
```

of KV cache.

That's enormous.

GQA reduces this substantially.

---

# 31. MHA, MQA and GQA

There are three useful attention configurations to understand.

With **MHA**, every query head has its own K and V heads.

For example:

```text
32 Q heads
32 K heads
32 V heads
```

This gives high KV memory usage.

With **MQA**, many query heads share a single K/V head.

For example:

```text
32 Q heads
1 KV head
```

This dramatically reduces KV memory.

With **GQA**, the model sits between those two.

For example:

```text
32 Q heads
8 KV heads
```

This provides a compromise between attention capacity and KV-cache efficiency.

Conceptually:

```text
MHA

Q Q Q Q Q Q Q Q
| | | | | | | |
K K K K K K K K


GQA

Q Q Q Q   Q Q Q Q   Q Q Q Q
  \ /       \ /       \ /
   K         K         K


MQA

Q Q Q Q Q Q Q Q
        |
        K
```

The exact grouping differs by implementation, but the memory principle remains the same.

---

# 32. Now let's derive a general formula you can use for any model

Whenever you encounter a transformer, identify five values:

```text
L  = number of layers

H  = number of KV heads

D  = head dimension

B  = bytes per KV element

S  = sequence length
```

The per-token KV-cache memory is:

```text
2 × L × H × D × B
```

The total KV-cache memory is:

```text
S × 2 × L × H × D × B
```

The `2` exists because we store:

```text
K
V
```

The `L` exists because every transformer layer has its own attention state.

The `H` exists because every KV head has its own K/V vectors.

The `D` exists because each head has that many values.

The `B` exists because each stored number occupies some number of bytes.

And `S` exists because we store K/V for every token.

# 33. Let's calculate the same model using FP16

FP16 also requires:

```text
2 bytes
```

So nothing changes.

For our model:

```text
32 layers
8 KV heads
128 head dimension
2 bytes
```

we get:

```text
2 × 32 × 8 × 128 × 2
```

Calculate step by step:

```text
2 × 32 = 64

64 × 8 = 512

512 × 128 = 65,536

65,536 × 2 = 131,072 bytes
```

Therefore:

```text
131,072 bytes/token
```

or:

```text
128 KiB/token
```

# 34. What if we use FP8?

Now assume:

```text
1 byte per element
```

Then:

```text
2 × 32 × 8 × 128 × 1
```

equals:

```text
65,536 bytes
```

Therefore:

```text
64 KiB/token
```

So compared with BF16:

```text
BF16:
128 KiB/token

FP8:
64 KiB/token
```

At 128K context:

```text
BF16 ≈ 16 GiB

```

This illustrates why KV-cache quantization can be so valuable for long-context serving.

---

# 35. What if the cache uses INT8?

The same basic arithmetic gives:

```text
1 byte
```

per stored element.

So again:

```text
64 KiB/token
```

However, real KV-cache quantization is more complicated than simply changing `2 bytes` to `1 byte`.

A production implementation needs to account for things such as quantization scales, zero points where applicable, per-channel or per-token schemes, kernel support, numerical error, and dequantization or fused quantized attention behavior.

So the simple formula gives the theoretical payload size, while actual runtime memory can be somewhat larger.

---

# 36. Why KV cache is usually GPU memory

During high-performance inference, the KV cache is generally placed in GPU memory because attention needs extremely fast access to it.

For example:

```text
GPU VRAM

Model weights
+
KV cache
+
activations
+
temporary buffers
+
CUDA/runtime allocations
```

All compete for GPU memory.

Suppose you have:

```text
24 GB GPU
```

and the model weights consume:

```text
16 GB
```

You might think:

```text
24 - 16 = 8 GB remaining
```

and therefore:

> "I can use 8 GB for the KV cache."

Not necessarily.

You still need memory for:

```text
CUDA runtime
temporary tensors
attention workspaces
activations
framework overhead
CUDA graphs
communication buffers
allocator fragmentation
```

Therefore, the actual usable KV-cache capacity is smaller.

This matters enormously in production inference.

# 37. Why batch size makes KV cache explode

Now suppose you're serving one user.

You have:

```text
batch size = 1
```

and:

```text
128K context
```

You might need approximately:

```text
16 GiB
```

of KV cache for our example architecture.

But suppose you serve:

```text
batch size = 8
```

and every request has approximately the same sequence length.

Then approximately:

```text
16 GiB × 8
```

equals:

```text
128 GiB
```

of KV cache.

This is why serving systems cannot simply say:

> "The model fits in GPU memory."

They must answer:

> "The model plus the expected KV cache for the target batch size and context length fits in GPU memory."

That's a much more useful production question.

# 38. A practical inference-memory equation

A simplified inference memory model is:

```text
Total GPU memory

≈

Model weights
+
KV cache
+
activations
+
temporary/workspace memory
+
runtime overhead
```

And:

```text
KV cache

≈

batch size
×
sequence length
×
2
×
number of layers
×
KV heads
×
head dimension
×
bytes per element
```

So if you're designing an inference server, you should think about all of these dimensions simultaneously.

# 39. Why long-context models are difficult to serve

Imagine a model supports:

```text
128K context
```

That does not mean:

> Every request will automatically consume 128K tokens.

But if the system allocates the maximum possible KV cache for every request, memory can be wasted.

For example:

```text
Request A = 1K tokens
Request B = 8K tokens
Request C = 32K tokens
Request D = 128K tokens
```

If you reserve 128K capacity for every request, you waste enormous amounts of memory.

This leads directly to one of the most important inference-system optimizations:

# Paged KV Cache

---

# 40. The idea behind paged KV cache

Traditional memory allocation can conceptually look like:

```text
Request A
[==============================]

Request B
[==============================]

Request C
[==============================]
```

Each request may receive a large contiguous region.

But sequences have different lengths and grow dynamically.

Paged approaches divide the KV cache into smaller blocks/pages.

Conceptually:

```text
GPU KV memory

[Page 1]
[Page 2]
[Page 3]
[Page 4]
[Page 5]
[Page 6]
...
```

A request might use:

```text
Request A → Page 2 → Page 7 → Page 11
```

Another:

```text
Request B → Page 1 → Page 3 → Page 9
```

The logical sequence remains contiguous from the model's perspective, but the physical memory doesn't need to be one giant contiguous allocation.

This is one of the ideas behind systems such as vLLM's PagedAttention architecture.

---

# 41. The connection to modern inference engines

Once you understand KV caching, several modern inference techniques become much easier to understand.

**PagedAttention** is primarily about efficiently managing KV-cache memory.

**Continuous batching** allows requests at different generation stages to share GPU execution efficiently.

**Prefix caching** allows reusable KV states from shared prefixes to be reused.

**KV-cache quantization** reduces the number of bytes needed per cached element.

**MQA and GQA** reduce the number of KV heads.

**Tensor parallelism** can distribute the KV cache and computation across multiple GPUs.

**Context parallelism** and related long-context techniques distribute sequence-related work across devices.

These are not isolated tricks.

They are responses to the same fundamental constraint:

> The KV cache becomes increasingly expensive as the amount of active context grows.

---

# 42. Prefix caching

Consider an application where every request begins with the same system prompt:

```text
You are an enterprise financial assistant...

[10,000-token company policy]

[10,000-token product documentation]
```

Then the user asks:

```text
What is the refund policy?
```

Another user asks:

```text
Can I cancel this subscription?
```

The first 20,000 tokens are identical.

Without prefix caching, you repeatedly compute the same K/V information.

With prefix caching, the system can potentially reuse the previously computed KV state for that shared prefix.

Conceptually:

```text
Shared prefix
       ↓
Cached KV
       ↓
   User A
     +
   User B
     +
   User C
```

This can significantly reduce prefill work in workloads with repeated prompts.

---

# 43. But there is an important limitation

KV cache is not simply some generic embedding of the conversation.

It is **layer-specific attention state**.

That means the cache is tied to things such as:

```text
model architecture
model weights
attention implementation
position encoding
token sequence
KV representation
```

You generally cannot take arbitrary KV tensors from one unrelated model and insert them into another model.

This becomes especially important when people discuss:

```text
KV transfer
cross-model KV reuse
KV cache sharing
```

Those techniques require careful compatibility between the models and representations.

---

# 44. Why positional encoding matters

The transformer needs to know where tokens occur in the sequence.

For example:

```text
dog bites man
```

is not necessarily equivalent to:

```text
man bites dog
```

Position information therefore affects attention.

Modern models may use mechanisms such as:

```text
RoPE
```

or other positional representations.

Because K/V representations are produced within the context of the model's positional mechanism, KV-cache reuse isn't simply:

> "These tokens look the same, so copy the cache."

The positional semantics and model architecture have to be compatible.

---

# 45. Another important distinction: prefill versus decode

When you use an LLM, there are effectively two very different workloads.

During **prefill**, the model processes many input tokens.

For example:

```text
100,000-token document
```

During **decode**, the model generates:

```text
one token
```

at a time.

The hardware behavior is different.

Prefill tends to have substantial parallel computation because many input tokens can be processed together.

Decode is much more dependent on repeatedly accessing the existing KV cache and generating one new token at a time.

This is why LLM inference discussions often distinguish:

```text
TTFT
```

meaning:

> Time To First Token

from:

```text
TPOT
```

meaning:

> Time Per Output Token

The KV cache is particularly central to the decode side.

---

# 46. A mental model that makes everything easier

Think of the KV cache like a notebook.

Suppose you're reading a 1,000-page book and answering questions about it.

Without a notebook, every time someone asks:

> "What did the author say about chapter 2?"

you reread the entire book.

That's inefficient.

Instead, while reading, you record important information in your notebook.

Then when someone asks a question, you consult your notes.

The transformer is doing something conceptually similar.

Instead of recalculating the K/V representations of every previous token:

```text
calculate once
     ↓
store
     ↓
reuse
```

That stored state is the KV cache.

The analogy isn't mathematically exact, but it is useful for building intuition.

---

# 47. The complete lifecycle of the KV cache

Let's put everything together.

You provide:

```text
"Explain attention mechanisms."
```

The tokenizer converts this into:

```text
Token 1
Token 2
Token 3
...
```

The model performs prefill.

For every layer, it generates K and V for every prompt token.

Those are stored:

```text
Layer 1 → K/V
Layer 2 → K/V
...
Layer 32 → K/V
```

The model generates the first output token.

For that new token, it calculates:

```text
Q
K
V
```

The new K and V are appended to the cache.

The Q attends over the entire available K/V history.

The model predicts another token.

Again:

```text
Qnew
Knew
Vnew
```

The new K/V are appended.

The process repeats:

```text
Prompt
  ↓
Prefill
  ↓
KV cache created
  ↓
Generate token
  ↓
Append K/V
  ↓
Generate token
  ↓
Append K/V
  ↓
Generate token
  ↓
Append K/V
  ↓
...
```

The cache therefore grows with the sequence.

For a standard transformer KV cache:

```text
KV bytes per token

=
2
×
number of layers
×
number of KV heads
×
head dimension
×
bytes per element
```

For an entire sequence:

```text
Total KV bytes

=
sequence length
×
2
×
number of layers
×
number of KV heads
×
head dimension
×
bytes per element
```

For a batch:

```text
Total KV bytes

=
batch size
×
sequence length
×
2
×
number of layers
×
number of KV heads
×
head dimension
×
bytes per element
```

That formula is enough to estimate the raw KV-cache payload for most standard decoder-only transformer architectures.

# 49. Our real-model calculation one final time

For the Llama 3 8B-style configuration:

```text
Layers       = 32
KV heads     = 8
Head dim     = 128
KV precision = BF16
Bytes        = 2
```

Plug them into:

```text
2 × layers × KV heads × head_dim × bytes
```

giving:

```text
2 × 32 × 8 × 128 × 2
```

Then:

```text
2 × 32 = 64

64 × 8 = 512

512 × 128 = 65,536

65,536 × 2 = 131,072 bytes
```

Therefore:

```text
131,072 bytes/token
```

which is:

```text
128 KiB/token
```

Then:

```text
8K tokens
≈ 1 GiB

16K tokens
≈ 2 GiB

32K tokens
≈ 4 GiB

64K tokens
≈ 8 GiB

128K tokens
≈ 16 GiB
```

That is the arithmetic you should be able to reproduce yourself rather than merely memorizing a number.

# 50. The deepest takeaway

The KV cache exists because autoregressive generation repeatedly needs information about previous tokens, but that information does not need to be recomputed every time.

The transformer creates Key and Value representations for each token at each layer. During generation, those representations are stored and reused. Only the newly generated token needs a new Query, Key, and Value calculation.

The fundamental memory cost is therefore determined by the number of layers, the number of KV heads, the head dimension, the number of tokens being retained, and the numerical precision used for the cache.

The most important formula is:

```text
KV bytes per token
=
2 × layers × KV heads × head dimension × bytes per element
```

The first `2` represents Key and Value.

And one of the most important modern architectural optimizations is that **KV heads can be much fewer than query heads**. That is exactly why GQA and MQA can dramatically reduce inference memory.

Once you understand this, a lot of modern LLM inference engineering becomes much less mysterious. When you encounter **PagedAttention, vLLM, continuous batching, prefix caching, KV quantization, GQA, MQA, speculative decoding, long-context inference, KV offloading, or KV-cache transfer**, you can trace most of the engineering decisions back to one underlying reality:

```text
More context
      ↓
More K/V state
      ↓
More memory
      ↓
More memory-management pressure
      ↓
Need for better inference systems
```

And that is the real reason the KV cache is one of the central pieces of modern LLM inference engineering.
